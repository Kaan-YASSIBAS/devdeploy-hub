# Deployment Update/Edit Flow v1 Design

Date: 2026-07-26

## Goal

Add a safe Deployment update/edit flow that changes an existing DevDeploy-managed workload through GitOps, then lets Argo CD reconcile the desired state. V1 updates are limited to image, replicas, container port, service port, and preview path.

## Current Create/Delete Model

DevDeploy currently treats database/domain records as product truth, the GitOps repository as desired-state truth, and Kubernetes/Argo CD as runtime and reconciliation truth.

Create flow:

- The backend validates the requested app and service settings.
- The backend creates or reactivates the linked `ServiceDefinition`.
- The backend creates a `DeploymentRecord` linked to that active service definition.
- The GitOps writer creates `deployment.yaml`, `service.yaml`, app `kustomization.yaml`, and updates the root workload kustomization.
- The backend commits and pushes the GitOps change.
- Argo CD syncs the Root Application.
- Runtime/read-only status enriches the product record.

Delete/destroy flow:

- The backend removes the app from GitOps desired state.
- The backend marks the `DeploymentRecord` destroyed/archived.
- Argo CD prunes the removed workload resources.
- The linked `ServiceDefinition` is archived only when no active deployment still uses it.

## Proposed Backend API Shape

Add a narrow update endpoint for owned active deployment records:

`PATCH /api/v1/deployment-records/{deployment_id}/gitops`

Request fields, all optional but at least one required:

- `image`
- `replicas`
- `container_port`
- `service_port`
- `preview_path`

Response should mirror the existing GitOps operation style:

- `status`: `pushed_waiting_for_argocd`, `no_changes`, or an honest failure status
- `deployment_id`
- `app_name`
- `commit_sha`
- `manifest_path`
- `message`
- normalized deployment record fields

The endpoint must be owner-scoped, reject archived/destroyed records, and never accept namespace, service name, repo path, or Argo CD app name from the client.

## GitOps Manifest Update Behavior

The update operation rewrites only the existing managed app manifest set:

- `apps/{app_name}/deployment.yaml`
- `apps/{app_name}/service.yaml`
- `apps/{app_name}/kustomization.yaml` only if needed for consistency
- root `kustomization.yaml` should normally remain unchanged

Behavior:

- Preserve the existing GitOps repository structure.
- Require the app directory to already exist and remain inside the managed source path.
- Preserve DevDeploy labels and namespace.
- Preserve hardened security context and runtime mounts already generated by the writer.
- Update Deployment image, replicas, selector-compatible pod labels, and container port as needed.
- Update Service port/targetPort consistently with the container port model.
- Do not manually patch Kubernetes runtime resources.
- Commit and push the Git change as the source of desired state.

If rendered manifests are unchanged, return `no_changes` and do not create a commit.

## Database Update Behavior

The backend updates the `DeploymentRecord` only after the GitOps repository update succeeds or is confirmed as `no_changes`.

Fields updated in v1:

- `image`
- `replicas`
- `container_port`
- `service_port`
- `preview_path`
- `desired_state`: likely `pending` while Argo CD catches up
- `commit_sha`
- `status_summary`

The existing record ID must remain stable. Update must not create a new active deployment record for the same app.

If Git commit or push fails, the DB record should not be advanced to the new desired values unless the repository state is known to match them.

## ServiceDefinition Behavior

The linked `ServiceDefinition` remains the product service identity.

V1 behavior:

- Preserve the existing `service_definition_id`.
- Do not archive or replace the service definition during update.
- If the deployment is linked to an archived service definition, repair/reactivate it before update or fail safely if ownership does not match.
- Keep `default_image`, `default_replicas`, and `default_port` behavior explicit. The safest v1 default is to update the deployment record without silently changing service defaults, unless the Services API is the caller.

This avoids hidden cross-aggregate mutation from deployment update into service-definition policy.

## Frontend UX Flow

Add an edit action on deployment detail and/or deployment card for active DevDeploy-managed deployments.

Form fields:

- Image
- Replicas
- Container port
- Service port
- Preview path

UX behavior:

- Pre-fill from the current `DeploymentRecord`.
- Disable app name and namespace in v1.
- Show a clear summary of what will change.
- Submit calls the update endpoint.
- Keep the user on the deployment detail page or return to the deployments list with progress visible.
- Existing access/preview buttons remain available when runtime is healthy.

## Update Progress States

Suggested frontend progress lifecycle:

- `validating`: validating update input
- `committing`: writing and pushing GitOps manifest changes
- `waiting_for_argocd`: waiting for Argo CD to observe the commit
- `reconciling`: Kubernetes rollout is progressing
- `ready`: runtime matches desired state and workload is ready
- `no_changes`: requested state already matches desired state
- `failed`: GitOps update or reconciliation failed honestly

The backend may initially remain synchronous for Git commit/push and return `pushed_waiting_for_argocd`. The frontend should poll existing deployment/reconcile/runtime status until the target commit and runtime state are observed.

## Failure Handling

Validation failure:

- Return `422` with field-specific validation details.

Missing or archived record:

- Return `404`, `403`, or `409` using existing ownership/archive conventions.

GitOps source missing or malformed:

- Return `409` with a safe message that the managed manifest set cannot be updated.

Commit/push failure:

- Return a GitOps failure status without leaking credentials or raw remote URLs.
- Do not mutate runtime directly.

Argo CD or runtime timeout:

- Keep the deployment in an honest pending/progressing state.
- Do not mark update complete until commit/revision and runtime evidence agree.

Runtime failure after sync:

- Surface degraded or failed reconcile state without rolling back automatically in v1.

## Validation Rules

General:

- Request must be owner-scoped.
- Deployment must be active and DevDeploy-managed.
- At least one editable field must be provided.
- Unknown fields are rejected.

Image:

- Required if provided to be non-empty.
- Must not contain whitespace or shell metacharacter-style control characters.
- No image build is performed in v1.

Replicas:

- Integer, minimum `1` for v1.
- Upper bound should match existing create validation.

Ports:

- `container_port` and `service_port` must be `1..65535`.
- Ports must be TCP in v1.
- Service targetPort should continue to map to the named container port where possible.

Preview path:

- Empty normalizes to `/`.
- Relative values like `ui` normalize to `/ui`.
- Reject absolute URLs, protocol-relative URLs, path traversal, backslashes, query-only, and fragment-only values.

## Smoke Test Checklist

nginx update smoke:

- Create `nginx` with `nginx:latest`, replicas `1`, port `80`.
- Update replicas to `2`.
- Confirm GitOps commit is pushed.
- Confirm Argo CD Root Application returns `Synced` / `Healthy`.
- Confirm Deployment ready replicas become `2/2`.
- Update replicas back to `1`.
- Delete `nginx` and confirm cleanup.

podinfo update/preview smoke:

- Use persistent `podinfo` preview smoke app.
- Update image tag or replicas within a safe known-good value.
- Confirm the deployment rolls out through Argo CD.
- Confirm preview still opens through the backend-owned route.
- Confirm `/api/info` runtime requests still route through the preview path.
- Confirm the main DevDeploy JWT and auth cookies are not forwarded upstream.

## Risks And Constraints

- Same-tag image updates may not roll pods unless image identity changes. V1 should document this and prefer explicit image tags/digests.
- Changing ports can temporarily break readiness, service access, and preview until rollout completes.
- Updating service port and container port must stay internally consistent to avoid a healthy pod with a broken service.
- The flow must not broaden Kubernetes RBAC.
- The flow must not manually patch runtime resources as the normal product path.
- Existing create/delete/preview behavior must remain stable.
- `podinfo` remains the persistent preview smoke app baseline.

## Implementation Phases

1. Backend domain/API foundation
   - Add update request/response schemas.
   - Add owner-scoped update endpoint.
   - Add validation and no-change detection.

2. GitOps writer update support
   - Add manifest update mode for existing app directories.
   - Preserve security context and labels.
   - Add focused render and path-safety tests.

3. Reconcile/status integration
   - Store commit SHA and pending status summary.
   - Reuse existing Argo CD/runtime read-only status for progress.
   - Add tests for synced, progressing, degraded, and timeout states.

4. Frontend edit UX
   - Add edit modal/page.
   - Add localized progress states.
   - Poll existing status endpoints until ready or degraded.

5. Live smoke validation
   - Run nginx update/delete smoke.
   - Run podinfo update/preview smoke.
   - Confirm Argo CD Root Application remains `Synced` / `Healthy`.
   - Confirm no workload resources are mutated outside GitOps.
